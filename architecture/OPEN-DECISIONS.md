# Open Decisions — Blocking Set

Six Open Decisions, identical in membership to the six the Round 5 consolidated audit (`docs/baseline/AUDIT-REPORT.md` §5–6) names as blocking, unchanged by the architecture work in `TASD-v1.0.md`. None is resolved by this architecture; each is listed here with the exact architectural area it gates and how the design accepts the eventual answer as configuration. The full 21-item Open Decision table (all decisions, blocking and non-blocking) is in `TASD-v1.0.md` §24.

| ID | Decision | Architectural area(s) affected | What is blocked until resolved | How the architecture accepts the answer |
|---|---|---|---|---|
| **OD-01** | Approval tier structure (single-tier / risk-tiered / fixed multi-stage) | Human Approval (§17), `poc_approval_request`/`approval_decision` schema (§11.6) | The RACI model stays an explicit single-tier placeholder; a tiered approval workflow cannot be built | `policy_config.approval_tier_model` reserved `NULL`; §11.9's `fn_evaluate_tier_preconditions` is an additive extension point over P1–P4, never a replacement for them |
| **OD-06** | Who formally holds the "Environment Owner" role | Environment Readiness (§16.2) | The attestation/sign-off workflow has no named accountable individual, only a role-claim check | `fn_attest_dimension` checks a role *claim*, not a specific person; the organization's answer is applied via RBAC/IdP group-mapping configuration (§8.4), no schema change needed |
| **OD-07** | Who may validate evidence (Security Reviewer only, or also Final Approver) and who judges sufficiency | Evidence Management (§15.2, §15.6) | Evidence can be uploaded and classified, but the validator population is fixed to Security Reviewer only until this resolves | `evidence_requirement.validator_role` enum already includes `FinalApprover` as an extension value; `fn_transition_evidence_state`'s role check reads this configuration |
| **OD-10** | Layer 1 Completeness threshold (the unusable-answer fraction that trips Insufficient Information) | Decision Engine Layer 1 (§14.4, §14.7) | Layer 1 Rule 3 cannot evaluate; the engine returns `REFUSED` rather than a false "Layer 1 passed" for any scope that would only fail on this rule | `policy_config.layer1_completeness_threshold`, `NULL`-gated — Rules 1–2 (Mandatory-domain coverage, readiness-not-submitted) function without it |
| **OD-15** | Layer 3 risk-factor weights (F1–F5), including the Pending-Review discount within F1 | Decision Engine Layer 3 (§14.5, §14.7) | **Layer 3 cannot run at all.** No `GO` recommendation can ever be issued | `policy_config.layer3_weights`, `NULL`-gated refusal of the entire layer — no default weight is substituted |
| **OD-16** | Layer 3 risk-score thresholds/tiers | Decision Engine Layer 3 (§14.5, §14.7) | Same as OD-15 — weights alone cannot produce a risk tier without cut points | `policy_config.layer3_thresholds`, `NULL`-gated alongside OD-15 |

## The load-bearing consequence

Until **OD-10, OD-15, and OD-16** are all resolved, the system **cannot issue a `GO` recommendation under any circumstance** — not a conservative one, not a flagged one (`TASD-v1.0.md` §14.7, §2.4). It can issue `Insufficient Information` once OD-10 is set, and `NO-GO` via the structural B-01/B-02 blockers, which need no Open Decision to function. Until **OD-01, OD-06, and OD-07** are resolved, the system has no named authority behind the Final Approver, Environment Owner, and evidence-validator roles respectively — it can be built and tested, but not meaningfully operated.

This is the same six-item blocking set the baseline has carried unchanged across all five documentation-audit rounds (`docs/baseline/AUDIT-REPORT.md` §5: "identical in membership across all five rounds"). The architecture work does not add to, remove from, or silently answer any item on this list.
